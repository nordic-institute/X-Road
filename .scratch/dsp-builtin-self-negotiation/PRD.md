## Problem

After `[[dsp-builtin-service-catalog]]` and `[[dsp-error-mapping]]` landed, built-in server-proxy services (`getSecurityServerMetrics`, `getSecurityServerOperationalData`, `getSecurityServerHealthData`, `listMethods`, etc.) appear in the DSP catalog with valid Xrd-PULL distributions. Catalog fetch succeeds (`datasets=7`), an offer is found, contract negotiation begins:

```
ContractNegotiation ... INITIAL → REQUESTING → REQUESTED → AGREEING → AGREED

ERROR: duplicate key value violates unique constraint
  "edc_contract_agreement_agr_agreement_id_agr_participant_con_key"
  Detail: Key (agr_agreement_id, agr_participant_context_id)=(<uuid>, ss0) already exists.

DSP: Cannot process ContractAgreementVerificationMessage because negotiation cannot be verified
ContractNegotiation ... → TERMINATING
... 60s timeout ...
network_error: Asset access acquisition timed out after 60s
```

Root cause is identical to the one `[[dsp-mgmt-dual-context]]` already solved for MANAGEMENT subsystem: a security server is hosting the asset locally, so both consumer and provider sides of the negotiation run against the **same** participant context (`ss0`). The `edc_contract_agreement` unique constraint on `(agreement_id, participant_context_id)` rejects the second write; verification then finds a CONSUMER-typed row, returns HTTP 409 ("negotiation cannot be verified"); the consumer-side stage times out at 60 s.

Built-in services are inherently self-hosted — every SS hosts them by definition. So every consumer call to a built-in on its own SS hits this collision.

## Decision

Mirror the management-dual-context pattern: built-in services own a distinct DSP identity so that self-negotiation produces two distinct `participantContextId` values, side-stepping the constraint collision.

Two viable shapes:

1. **Reuse the existing `<host>-mgmt` context.** Built-ins tag with the mgmt ctx in the catalog; consumer-side routes built-in service codes to the mgmt counter-party target. Pros: zero new bootstrap. Cons: conflates "mgmt subsystem" with "local-handler services" — they're different conceptual roles even if the runtime trick is the same.

2. **Introduce a new `<host>-builtin` context.** Built-ins tag with builtin ctx; consumer-side routes built-in service codes to a new builtin counter-party target. Pros: clean separation; matches the conceptual model. Cons: requires `00-setup-dsp.hurl` and the systemtest `DspBootstrap` to provision a third context (`<host>-builtin`) alongside `<host>` and `<host>-mgmt`.

**Recommendation: (1)** for v1 to minimize churn. The mgmt context already covers "stuff hosted by this SS that creates self-negotiation when consumer == provider"; built-ins fit the same shape. If we later need to distinguish them for policy or operational reasons, splitting is mechanical.

If the team prefers conceptual cleanliness, (2) is the right long-term answer.

## Design (option 1)

### Catalog tagging

`BuiltinServiceCatalog` is currently constructed with the **host** context. Change `AssetIndexServerConfStore`, `ContractDefinitionServerConfStore`, `PolicyDefinitionServerConfStore` so that when emitting built-in synthetic entries, they use `managementParticipantContextId` instead of `participantContextId`.

This is a small targeted change — only the **builtin** branches in each store. The serverconf-backed branches stay on the host context exactly as today.

### Consumer-side routing

`ConsumerSideDspProcessor.execute()` currently picks `mgmtCounterPartyTargets` when `request.managementSubsystem()` is true. The flag is set by `Client{Soap,Rest}MessageProcessor.isManagementRequest(serviceId)`.

Add a parallel check: `isBuiltinService(serviceId)` returns true when `serviceId.getServiceCode()` matches one of the known built-in codes (canonical list from `BuiltinServiceCatalog` — duplicate as a constants holder in `proxy-core` since cross-module class access is not desirable, and add a unit test that asserts the lists match).

Then in the processor:

```java
var targets = (request.managementSubsystem() || request.builtinService())
        ? mgmtCounterPartyTargets
        : counterPartyTargets;
```

`DspRequest` gains a third boolean `builtinService`. The flag is plumbed through from `ClientSoapMessageProcessor.processRequest` / `ClientRestMessageProcessor.processRequest`.

### Why not just add the routing in the processor?

The catalog tagging change is required because EDC filters `ContractDefinitionStore.findAll(...)` results by `participantContextId` matching the **routed** context. If built-in contract definitions are tagged with `ss0` but the consumer routes the catalog request at `ss0-mgmt`, the catalog returns empty. Both ends must agree on the context.

### Tests

1. **Unit:** update `AssetIndexServerConfStoreTest`, `ContractDefinitionServerConfStoreTest`, `PolicyDefinitionServerConfStoreTest`: built-in entities tagged with mgmt ctx, not host ctx. (Inverts the current assertion.)
2. **Unit:** update `BuiltinServiceCatalogTest` for any constructor signature changes.
3. **Unit:** new `ConsumerSideDspProcessorTest` scenarios — built-in request routes to mgmt counter-party target; both managementSubsystem AND builtinService true uses mgmt target; neither uses host target.
4. **Unit:** parity test in `:service:proxy:proxy-core` between proxy-core built-in service code constants and the catalog module's `BuiltinServiceCatalog` constants — fails on drift.
5. **System tests:** after fix, `2100`, `2200`, `2400` should pass (proxymonitor + opmonitor + messagelog). The `0920` tests will still fail because they expect pre-edc17 error codes (`io_error`, `serverproxy.service_failed.unknown_member`); that gap is separate.

## Out of scope

- `0920 Other Security Server connection test` and `0920 Management Security Server test fails`. Their expected error codes (`server.clientproxy.io_error`, `server.serverproxy.service_failed.unknown_member`) belong to the pre-edc17 routing path. With DSP, the catalog miss is detected on the consumer side and produces `server.clientproxy.proxy.unknown_member`. Either:
  - Update test assertions to match the new architecture (recommended — the new code IS semantically correct: "unknown member" is exactly the issue), or
  - Add a special-case in the classifier to emit `IO_ERROR` for the "Other Security Server" diagnostic flow.
- Selenide login flake (`Automatic logout happens when timeout passes`) — unrelated.
