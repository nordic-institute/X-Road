## Problem

DSP-layer failures collapse rich X-Road error semantics into a generic `NETWORK_ERROR`. Two paths today:

1. **Control-plane side** — `AssetAccessGrpcService.acquire()` (lines 67-123) propagates `EdcException` directly. `RpcResponseHandler.handleException()` wraps any uncaught throwable as `XrdRuntimeException.systemException(exception)` which defaults to `INTERNAL_ERROR`. The string-payload `"No dataset found for asset ID: …"` is preserved but the **error code** is wrong.
2. **Consumer-proxy side** — `ConsumerSideDspProcessor.execute()` (lines 79-118) catches all per-candidate `RuntimeException`s and at exhaustion throws `XrdRuntimeException.systemException(NETWORK_ERROR, …, "All %d candidate security servers failed …")` (line 115), masking whatever specific code the control-plane reported.

System-tests asserting concrete error codes break:
- `0920 Other Security Server connection test` expects `server.clientproxy.io_error`.
- `0920 Management Security Server test fails` expects `server.serverproxy.service_failed.unknown_member`.

Both worked pre-edc17 because the request reached the **provider** server proxy, where the missing service produced a SOAP fault `server.serverproxy.service_failed.unknown_member` natively, which the consumer surfaced. Post-edc17 the request never crosses the wire — catalog miss kills it on the consumer side.

## Goal

Preserve the X-Road error contract: when a target service or member doesn't exist or isn't reachable, the consumer sees the same `ErrorCode` it always did, not `NETWORK_ERROR` or `INTERNAL_ERROR`.

## Decision

Two-part fix, both can ship in one change-set but the layers are independent enough to design separately.

### Part 1 — Control-plane: classify EDC failures into X-Road error codes

Inside `AssetAccessGrpcService.acquire()`, intercept the result of `awaitResult(...)` and any thrown `EdcException`. Classify by message / failure type and rethrow as `XrdRuntimeException` with a specific `ErrorCode`:

| EDC failure shape | New `ErrorCode` | Rationale |
|---|---|---|
| `"No dataset found for asset ID: …"` (catalog miss) | `UNKNOWN_MEMBER` | Closest existing equivalent of "the thing you're calling doesn't exist on the provider". Matches pre-edc17 `server.serverproxy.service_failed.unknown_member`. |
| `"No offers found for asset ID: …"` | `UNKNOWN_MEMBER` | Same class. |
| `"No PULL distribution found for asset ID: …"` | `SERVICE_FAILED` | Service exists but is mis-configured — closer to `service_failed` than `unknown_member`. |
| `"Failed to fetch catalog: …"` (catalog fetch failed at protocol layer) | `NETWORK_ERROR` | Genuine I/O failure to provider's DSP endpoint. Maps to `server.clientproxy.io_error`. |
| `awaitResult` `TimeoutException` | `NETWORK_ERROR` | Already the right class. |
| `"Failed to resolve participant context: …"` | `INTERNAL_ERROR` | Local config issue. |
| Other / unknown `EdcException` | `SERVICE_FAILED` | Default — preserve message, no claim about cause. |

Classification implementation: a small `DspFailureClassifier` utility with one method `XrdRuntimeException classify(Throwable cause)`. Pattern-match by the orchestrator's exception messages (already constants in `AssetAccessOrchestrator`) — keep both in sync via a shared constants holder if needed, but simpler is to match against the prefixes which are stable in `AssetAccessOrchestrator.java:164`, `167`, `177`, `135`, `153`.

Wrap the call inside `acquire(...)` so all paths go through the classifier:

```java
try {
    // existing body
} catch (EdcException | RuntimeException e) {
    throw DspFailureClassifier.classify(e);
}
```

`XrdRuntimeException` propagates over gRPC as-is via `RpcResponseHandler.handleException()` (already calls `XrdRuntimeException.systemException(exception)` — but when the exception **is** already an `XrdRuntimeException`, the builder preserves the original code; verify this).

### Part 2 — Consumer-proxy: don't collapse the last failure

`ConsumerSideDspProcessor.execute()` today throws `NETWORK_ERROR` regardless of what the per-candidate failures were. Change:

1. If **all** candidates failed with the **same** `ErrorCode` (and that code came from an `XrdRuntimeException` returned over gRPC, not from a target lookup miss), rethrow with that code.
2. If failures are mixed, or originated locally (e.g., `"No DSP counter-party target configured …"`), keep current `NETWORK_ERROR` behavior — that's a genuine routing-table problem.
3. Special-case zero candidates after `providerSecurityServerResolver.resolve()`: throw `UNKNOWN_MEMBER` directly (no negotiation attempted means no candidates exist — that's an unknown member).

Simplification: extract `XrdRuntimeException` if present; otherwise fall back to `NETWORK_ERROR`. Pseudocode:

```java
private RuntimeException buildFinalException(List<RuntimeException> failures, ServiceId serviceId) {
    var xrdCodes = failures.stream()
            .filter(XrdRuntimeException.class::isInstance)
            .map(XrdRuntimeException.class::cast)
            .map(XrdRuntimeException::getErrorCode)
            .collect(Collectors.toSet());
    if (xrdCodes.size() == 1) {
        // homogeneous — preserve the code
        return failures.stream()
                .filter(XrdRuntimeException.class::isInstance)
                .findFirst().orElseThrow();
    }
    return XrdRuntimeException.systemException(NETWORK_ERROR, lastOf(failures),
            "All %d candidate security servers failed to acquire asset access for service %s",
            failures.size(), serviceId);
}
```

## Acceptance criteria

1. **New unit test** `DspFailureClassifierTest` (in `:service:ds-control-plane:ds-xroad-asset-access-api` test module) — exhaustive table-driven test of the EDC-message → ErrorCode mapping.
2. **Extended** `AssetAccessGrpcServiceTest` (create if missing) — given orchestrator returning `failed(...)` with each shape, the gRPC handler sends back `StatusRuntimeException` carrying `XrdRuntimeExceptionProto` with the expected code.
3. **Extended** `ConsumerSideDspProcessorTest`:
   - All candidates fail with the same `XrdRuntimeException(UNKNOWN_MEMBER)` → final exception carries `UNKNOWN_MEMBER`.
   - All candidates fail with the same `XrdRuntimeException(NETWORK_ERROR)` → final exception carries `NETWORK_ERROR`.
   - Mixed codes across candidates → fall back to `NETWORK_ERROR`.
   - `providerSecurityServerResolver.resolve(...)` returns empty list → `UNKNOWN_MEMBER`.
   - Local "no counter-party target" failure mixed with remote failures → still `NETWORK_ERROR`.
4. After fix: `0920 Other Security Server connection test` and `0920 Management Security Server test fails` pass.

## Out of scope

- Built-in catalog coverage — handled in parallel by `dsp-builtin-service-catalog`. Once that lands, catalog-miss on built-ins no longer happens, but `UNKNOWN_MEMBER` mapping is still the right behavior when a genuine unknown service is called.
- Restructuring `AssetAccessOrchestrator` failure types into a typed `Result.Failure` hierarchy. Cleaner long-term but out of scope here — string-message matching is acceptable given the failure messages are constants in one file.
- gRPC client-side classification — `AbstractRpcClient.handleGenericStatusRuntimeException()` already restores `XrdRuntimeException` from the wire correctly. No changes needed there.

## Risk / rollback

- Error code mapping is a behavior change: any callers that test for `NETWORK_ERROR` everywhere will need updates. Search for usages: `grep -rn "NETWORK_ERROR" src/security-server/system-test src/security-server/e2e-test`. None are expected to depend on the post-edc17 over-broad `NETWORK_ERROR` since these tests pre-date edc17.
- Pattern matching on EDC's English failure messages is fragile across EDC upgrades. Mitigation: the messages are local to `AssetAccessOrchestrator` and only that file emits them — guarded by tests on the classifier.
- All changes are additive within the two modules; no SPI / config / DB changes.
