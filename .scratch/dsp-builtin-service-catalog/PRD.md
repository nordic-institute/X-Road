# PRD — DSP Catalog Coverage for Built-in Server-Proxy Handler Services

> *This was generated by AI during triage.*

**Status:** ready-for-agent
**Owner:** unassigned
**Touch points:**
- `core/src/service/ds-control-plane/ds-xroad-catalog/` (asset / contract-def / policy-def server-conf stores)
- `core/src/service/proxy/proxy-core/src/main/java/org/niis/xroad/proxy/core/serverproxy/ServiceHandlerLoader.java` (built-in handler enumeration, source of truth)
- `core/src/service/proxy/proxy-core/src/main/java/org/niis/xroad/proxy/core/addon/{proxymonitor,opmonitoring,metaservice}/` (handler `SERVICE_CODE` constants)

---

## Problem

`AssetIndexServerConfStore.queryAssets()` enumerates only services from `serverConfProvider.getMembers()` × `getAllServices(member)`. Built-in SOAP handlers wired in `ServiceHandlerLoader.java:84-100` — `ProxyMonitorServiceHandlerImpl` (`getSecurityServerMetrics`), `OpMonitoringServiceHandlerImpl` (`getSecurityServerOperationalData`, `getSecurityServerHealthData`), `MetadataServiceHandlerImpl` (`listMethods`, `allowedMethods`, `getWsdl`, `getOpenAPI`) — are **never** registered in serverconf. They're hardcoded server-proxy dispatchers.

Result: every consumer DSP catalog request for these service IDs returns `datasets=0`. `AssetAccessOrchestrator.findOffer()` (`AssetAccessOrchestrator.java:164`) throws `EdcException("No dataset found for asset ID: …")`. Before edc17 cut-over, these services worked because the consumer proxy bypassed catalog and went straight to the provider server proxy, where the built-in handlers picked up the service code.

Concretely fails in `core/src/security-server/system-test`:
- `2100 Proxymonitor responds with correct response` (+ `TotalPhysicalMemory` variant)
- `2200 Messagelog contains metrics requests`
- `2400 Operational Data` / `2400 Health Data`

Pre-edc17 LXD setup also depended on this behavior — there's no mechanism today that surfaces a built-in handler as a DSP asset.

## Decision

Treat each enabled built-in server-proxy handler as a synthetic catalog entity owned by the **SS itself** (the owner `ClientId` from `serverConfProvider.getIdentifier().getOwner()`). The catalog stores must, in addition to enumerating serverconf services, enumerate the active built-in handlers and emit:

1. **Asset** with `assetId = <owner-encoded>:<serviceCode>` — same encoding scheme as `AssetMapper.encodeAssetId(ServiceId)`. No subsystem segment (built-ins are member-level on the SS owner).
2. **ContractDefinition** that grants access to that asset under an "everyone" / `acceptAll` policy (built-ins have access enforcement inside the handler itself, e.g. `ProxyMonitorServiceHandlerImpl.verifyAccess()`; the DSP catalog does not need to gate them).
3. **PolicyDefinition** matching the above.
4. **DataAddress** (`resolveForAsset`) pointing to the local server proxy with a synthetic baseUrl that the data-plane / server-side dispatcher recognizes as "route to built-in handler".

Mgmt-ctx vs host-ctx tagging: built-ins are non-MANAGEMENT — always tag with `participantContextId` (the host context), never with `managementParticipantContextId`.

## Design

### New component: `BuiltinServiceCatalog`

Package: `org.niis.xroad.edc.extension.catalog` (same package as the stores).

Responsibility: return the list of `(ServiceId.Conf, Asset, ContractDefinition, PolicyDefinition, DataAddress)` tuples for **active** built-in handlers on this SS.

Input: which built-ins are enabled (from `ProxyProperties.addon().metaservices().enabled() / opMonitor().enabled() / proxyMonitor().enabled()`). The catalog module does not depend on `proxy-core` (it lives in `ds-control-plane`). Wire enabled flags via:
- New config keys under `xroad.dsp.builtin-services.<name>.enabled` (default `true`), surfaced via `ServiceExtensionContext.getSetting(...)` in `XRoadServerConfCatalogExtension.initialize()`.
- Alternative: a new `BuiltinServiceCatalogProvider` SPI implemented in a small bridge module that `ds-control-plane-application` includes. Prefer the config-key approach — simpler, no new module.

Static service-code list (initial):
```
getSecurityServerMetrics        — proxyMonitor
getSecurityServerOperationalData — opMonitor
getSecurityServerHealthData      — opMonitor
listMethods                      — metaservices
allowedMethods                   — metaservices
getWsdl                          — metaservices
getOpenAPI                       — metaservices
```
Keep this list as a single source-of-truth constant. The proxy-core constants (`OpMonitoringRequests.GET_SECURITY_SERVER_OPERATIONAL_DATA`, `ProxyMonitorServiceHandlerImpl.SERVICE_CODE`, `MetadataRequests.LIST_METHODS`, etc.) cannot be imported here (cross-module). Duplicate as documented constants; add a unit test that asserts the catalog list matches the proxy-core constants (load via reflection from classpath in a test-only sibling, or duplicate + compare in a verification test in `:service:proxy:proxy-core` if dep direction allows).

### Owner identity

`ServerConfProvider.getIdentifier()` returns `SecurityServerId.Conf` whose `getOwner()` is the `ClientId.Conf` of the SS owner. Build synthetic `ServiceId.Conf` with that owner + service code (no subsystem, no version).

### Store changes

**`AssetIndexServerConfStore`:**
- `queryAssets(QuerySpec)`: after the existing serverconf-driven loop, append one synthetic Asset per enabled built-in. Reuse `AssetMapper.toAsset(serviceId, participantContextId)` — built-ins are tagged with the **host** context (`participantContextId`), never the mgmt context.
- `findById(String)`: when serverconf lookup fails, decode the asset ID; if its service code matches a built-in and the member matches `getIdentifier().getOwner()`, return the synthetic Asset.
- `resolveForAsset(String)`: built-ins return a `DataAddress` whose `baseUrl` points to the local server proxy with a marker the dispatcher can recognize — e.g. a reserved scheme `xroad-builtin://serverproxy/<serviceCode>` — OR the existing server-proxy URL pattern, but flagged via a property. Pick what data-plane already knows how to route. **See "Open question on data address" below.**
- `countAssets`: include built-ins in count.

**`ContractDefinitionServerConfStore`:**
- `findAll(QuerySpec)`: append one ContractDefinition per enabled built-in. Reuse the existing ContractDefinitionMapper or extend it with a "for built-in" variant that produces a single subject (the asset id) with an `acceptAll` policy reference.
- `findById(String)`: handle synthetic IDs (recognize the built-in service-code suffix).

**`PolicyDefinitionServerConfStore`:**
- Same shape — emit one `acceptAll` policy per built-in.

### Open question on data address

The current data-plane (`proxy-dsp-core` `XRoadDataPlaneSignalingApiController` + friends) routes resolved data addresses to provider URLs. For built-ins, the resolved URL must land in the **server-proxy** ServiceHandler chain so `ProxyMonitorServiceHandlerImpl.canHandle()` etc. fires. Two options:

1. **Synthetic baseUrl, dispatcher detects:** `HttpDataAddress` with `baseUrl = http://localhost:<serverProxyPort>/` (HTTP, internal). The server proxy already routes by SOAP service code — the existing handler chain runs naturally. Same path as current LXD setup (consumer → mTLS → provider server proxy → `ServiceHandlerLoader.getSoapHandlers()` dispatches by service code).
2. **Marker property:** Add `xroad.builtin=true` on the asset/data-address; data-plane uses local server-proxy URL when set. More explicit but requires data-plane changes.

**Recommendation: (1)**. The server-proxy URL is already the right destination; the SOAP dispatcher key is the service code in the SOAP envelope, which the consumer already preserves. No data-plane changes needed. Tests verify by asserting `resolveForAsset` returns an `HttpDataAddress` whose `baseUrl` resolves to the SS owner's server-proxy address (from global conf — `globalConfProvider.getProviderAddress(serverId)` style lookup, or a config-resolved local server-proxy URL).

### Acceptance criteria

1. New unit test: `BuiltinServiceCatalogTest` — verifies the canonical list of built-in service codes and that toggling each `enabled` flag adds/removes synthetic entities.
2. Extended `AssetIndexServerConfStoreTest`:
   - With no serverconf services, `queryAssets` still returns N built-in assets when all addons enabled.
   - `findById` returns synthetic Asset for `<owner>:getSecurityServerMetrics`.
   - `findById` returns null for unknown service codes (regression guard).
   - Built-ins tagged with host context, never mgmt context.
   - `resolveForAsset` returns a non-null DataAddress for each built-in.
3. Extended `ContractDefinitionServerConfStoreTest` + `PolicyDefinitionServerConfStoreTest` — analogous coverage.
4. After fix: `2100`, `2200`, `2400` system-test scenarios pass without seeding any new services into serverconf.

### Out of scope

- `OperationalDataRequest` payload validation. Tests just assert HTTP 200 + valid XML shape; existing handlers already do this end-to-end.
- Health-data response content. Same.
- Auth — built-ins do their own auth checks inside the handler; DSP policy is `acceptAll`.

## Implementation steps (suggested order)

1. Define `BuiltinServiceCatalog` with the canonical list + `enabled()` accessors backed by `ServiceExtensionContext` settings (default true).
2. Write `BuiltinServiceCatalogTest` first — drive the API shape.
3. Extend `AssetIndexServerConfStore` — inject `BuiltinServiceCatalog`, append in `queryAssets`/`findById`/`resolveForAsset`. Extend test.
4. Extend `ContractDefinitionServerConfStore` similarly. Extend test.
5. Extend `PolicyDefinitionServerConfStore` similarly. Extend test.
6. Wire into `XRoadServerConfCatalogExtension.initialize()` — instantiate `BuiltinServiceCatalog`, pass to each store constructor.
7. Local sanity: `./gradlew :service:ds-control-plane:ds-xroad-catalog:test`.
8. **Do not run system-tests yet** — wait for Fix B (`dsp-error-mapping`) to land. Then run jointly.

## Risk / rollback

- If built-in catalog entries leak into MANAGEMENT participant context, mgmt-subsystem catalogs grow unexpectedly. Mitigation: assert in tests that mgmt-ctx-filtered queries exclude built-ins.
- If `resolveForAsset` URL is wrong (option 1 above), provider-side server proxy never receives the request. Mitigation: integration smoke test inside the catalog module that asserts the URL matches the SS server-proxy URL pattern from global conf.
- All changes are additive — disabling all built-in flags returns to pre-fix behavior.
