# Agent Brief — DSP Catalog Coverage for Built-in Server-Proxy Handler Services

> *This was generated by AI during triage.*

## Mission

Built-in server-proxy SOAP handlers (`getSecurityServerMetrics`, `getSecurityServerOperationalData`, `getSecurityServerHealthData`, `listMethods`, `allowedMethods`, `getWsdl`, `getOpenAPI`) are hardcoded service dispatchers wired in `ServiceHandlerLoader.java:84-100`. They are not in serverconf, so the DSP catalog stores in `core/src/service/ds-control-plane/ds-xroad-catalog/` return `datasets=0` for them. Consumer requests fail with `EdcException("No dataset found …")` from `AssetAccessOrchestrator.java:164`.

Extend the catalog to emit synthetic `Asset` / `ContractDefinition` / `PolicyDefinition` for the active built-in handlers, owned by the SS owner `ClientId` from `serverConfProvider.getIdentifier().getOwner()`, tagged with the **host** participant context (never mgmt).

## Approach

1. **Test-first.** Write `BuiltinServiceCatalogTest` driving the new class API. Then extend the three existing `*ServerConfStoreTest` classes to cover the new behavior **before** modifying the stores.
2. **Single source of truth.** Define the canonical built-in list once in `BuiltinServiceCatalog` (constants for the seven service codes grouped by addon name). Add a verification test that fails if a constant drifts from what `proxy-core` defines (`OpMonitoringRequests`, `ProxyMonitorServiceHandlerImpl.SERVICE_CODE`, `MetadataRequests`).
3. **Wire via `ServiceExtensionContext` settings** (`xroad.dsp.builtin-services.{name}.enabled`, default true). Do not add a new module dependency.
4. **Data address (see PRD "Open question"):** use `HttpDataAddress` with baseUrl pointing to the SS owner's server-proxy URL (option 1 in PRD). Do NOT change data-plane code.
