# Test Setup — Spec-bound MSW Handlers

## Overview

MSW handlers in this directory are spec-bound: every path, HTTP method, and
response status is checked against the CS OpenAPI spec at type-check time.
Response body shapes are validated against the spec's JSON schemas at module
load time (AJV). Fixture values are real-shape, schema-valid, synthetic values.

## Adding a spec-bound handler

```ts
import { specHttp } from './spec-http';

// Path must exist in the spec, method must be defined for that path,
// status code must be listed in the spec's responses — tsc rejects anything else.
specHttp.get('/members/{member_id}', ({ params, response }) => {
  return response(200).json(yourFixture);
});
```

`specHttp` is created with `createOpenApiHttp<paths>({ baseUrl: '/api/v1' })`.
The `paths` type comes from `src/openapi-msw-paths.d.ts` (generated by
`openapi-typescript` from the CS OpenAPI spec).
Run `pnpm run generate-msw-types` after editing the OpenAPI spec to regenerate.

For endpoints not in `openapi-definition.yaml` (e.g. `/notifications/session-status`,
`/notifications/alerts`), use `specHttp.untyped.get(...)` with the full absolute
path including `/api/v1/`.

## Adding runtime schema validation

Call `validateBody(schema, fixture)` at **module load time** (top level, outside
handler functions). Validation inside a handler body is swallowed by the Service
Worker thread and never reaches the test runner.

```ts
import { validateBody } from './spec-http';

const mySchema = {
  type: 'object',
  required: ['client_id'],
  properties: { client_id: { type: 'object' } },
};

// Place this call at top level so a drifted fixture fails on module import
validateBody(mySchema, myFixture);
```

## Golden fixtures

Fixture JSON files live in `tests/setup/golden/`. They have real shape and
pass AJV schema validation; their values are synthetic (not captured from a
live backend).

When the backend response shape changes, edit the JSON files by hand to match
the updated OpenAPI schema, then run `pnpm run test` — the module-load AJV
validation fails on any fixture that no longer matches its schema.

## CS-specific notes

- **render-route.ts** creates a fresh pinia per test (with `createPersistedState({storage: sessionStorage})`),
  patches `useUser` (authenticated + permissions) and `useSystem` (sets
  `initialization_status` with real values so `isServerInitialized` returns true,
  preventing the `/init` redirect). It does NOT use the shared-ui singleton pinia.
- **Bootstrap mode** (`bootstrap: true`) installs the real `createXrdRouter` guard
  and boots unauthenticated — for testing guard redirects.
- **Session** (`session: 'expired'`) boots with `appState.setSessionAlive(false)`,
  causing `XrdApp` to render the session-expired dialog.
- **DEFAULT_PERMISSIONS** covers the main CS navigation tabs
  (VIEW_MEMBERS, VIEW_SECURITY_SERVERS, VIEW_MANAGEMENT_REQUESTS, VIEW_GLOBAL_GROUPS).

## Browser-mode limitations

Browser-mode specs do NOT fail on thrown errors or unhandled promise rejections.
Only a failed `expect()` assertion turns a spec red. Always assert observable
behaviour explicitly after any action that could fail.
