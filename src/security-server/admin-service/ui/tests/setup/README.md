# Test Setup — Spec-bound MSW Handlers

## Overview

MSW handlers in this directory are spec-bound: every path, HTTP method, and
response status is checked against the OpenAPI spec at type-check time.
Response body shapes are validated against the spec's JSON schemas at module
load time (AJV). Fixture values are real-shape, schema-valid, synthetic values;
refresh them from a live Security Server stack via `capture.sh` when one is
available.

## Adding a spec-bound handler

```ts
import { specHttp } from './spec-http';

// Path must exist in the spec, method must be defined for that path,
// status code must be listed in the spec's responses — tsc rejects anything else.
specHttp.get('/your-resource/{id}', ({ params, response }) => {
  return response(200).json(yourFixture);
});
```

`specHttp` is created with `createOpenApiHttp<paths>({ baseUrl: '/api/v1' })`.
The `paths` type comes from `src/openapi-msw-paths.d.ts` (generated by
`openapi-typescript` from the same YAML the `@hey-api/openapi-ts` types use).
Run `pnpm run generate-msw-types` after editing the OpenAPI spec to regenerate.

For endpoints not defined in `openapi-definition.yaml` (e.g.
`/notifications/session-status`, `/notifications/alerts`), use
`specHttp.untyped.get(...)` — the regular MSW `http` wrapper with full absolute
path including `/api/v1/`.

## Adding runtime schema validation

Call `validateBody(schema, fixture)` at **module load time** (top level, outside
handler functions). Validation inside a handler body is swallowed by the Service
Worker thread and never reaches the test runner.

```ts
import { validateBody } from './spec-http';

const mySchema = {
  type: 'object',
  required: ['id', 'name'],
  properties: {
    id: { type: 'string' },
    name: { type: 'string' },
  },
};

// Place this call at top level so a drifted fixture fails on module import
validateBody(mySchema, myFixture);
```

The schema objects are derived from the `components/schemas` section of
`openapi-definition.yaml`. For enum fields use the same enum values the spec
defines (e.g. `{ type: 'string', enum: ['HTTP', 'HTTPS', 'HTTPS_NO_AUTH'] }`).

## What the schema validator catches

- Wrong field type (`number` where `boolean` is required)
- Missing required fields
- Enum value not in the allowed set (e.g. a `connection_type` the spec forbids)

It does NOT check statuses or path correctness — those are the type-checker's
job. It does NOT validate business-rule correctness (e.g. that a `REGISTERED`
client actually has a cert) — that is the API tier's job.

## Golden fixtures

Fixture JSON files live in `tests/setup/golden/`. They have real shape and
pass AJV schema validation; their values are synthetic (not captured from a
live backend). Run `capture.sh` against a live Security Server stack to
refresh fixture values with real backend responses when a stack is available
(see `tests/setup/golden/capture.sh`).

To refresh fixtures when the backend response shape changes:

1. Boot the Security Server API-test stack:
   ```sh
   # From core/src/security-server/api-test:
   ./gradlew intTest
   ```
2. Run the capture script (requires a running stack at `$SS_HOST`):
   ```sh
   SS_HOST=https://localhost:4200 \
   SS_USER=xrd \
   SS_PASS=secret123! \
   bash tests/setup/golden/capture.sh
   ```
   The script records responses to `tests/setup/golden/*.json`.

3. Verify the module-load validation still passes: `pnpm run test`.

If no live stack is available, update the JSON files manually to match the
new spec shape and ensure `validateBody` passes (a failing validation surfaces
as a module-load error when tests run).

## In-flight loading state (latency patterns)

Use `delay()` from `msw` to hold a response open so the in-flight UI state
can be asserted before the response lands.

### Race-free pre-registration

Mount-time requests (fired in `created()` / `onMounted()`) may hit the Service
Worker before `worker.use()` inside `renderRoute` has propagated. Pre-register
the delayed handler **before** calling `renderRoute` to avoid this race:

```ts
import { delay } from 'msw';
import { worker } from '../setup/browser-setup';
import { specHttp } from '../setup/spec-http';

worker.use(
  specHttp.get(
    '/clients',
    async ({ response }) => {
      await delay(200);          // finite delay — response will land on its own
      return response(200).json(clientsFixture);
    },
    { once: true },              // only delay the first request; fall through after
  ),
);

await renderRoute('/clients');
await expect.element(page.getByRole('progressbar')).toBeVisible();
// rows appear once the delayed response lands:
await expect.element(page.getByTestId('client-name').first()).toBeVisible();
```

`{ once: true }` is essential: without it, every subsequent `GET /clients`
(re-renders, polling, reactivity) hits the delayed handler again and the loading
state never clears.

Use `delay('infinite')` only for user-action-triggered requests (POST, PUT,
DELETE) that fire after user interaction — those have no mount-time race. For
mount-time GETs always use a finite delay with `{ once: true }`.

### VDataTable loading row

`VDataTable` with `:loading="true"` renders a `<tr class="v-data-table-progress">`
containing a `VProgressLinear` with `role="progressbar"` and `aria-hidden="false"`.
The row is removed from the DOM when loading clears — it is not just hidden.
Assert presence with `page.getByRole('progressbar')`.

### VBtn loading state

`VBtn` with `:loading="true"` sets `aria-busy="true"` on the underlying
`<button>` element. It does **not** set the HTML `disabled` attribute.
Use `toHaveAttribute('aria-busy', 'true')` to assert in-flight state;
`toBeDisabled()` will fail.

## Auth / session / error-nav

### Auth model

- **Cookie-session only.** No client-side CSRF/XSRF token attach, no axios
  interceptors. CSRF testing is out of scope for component tests.
- `setupAddErrorNavigation(router, { 404: { name: RouteName.NotFound } })` is
  wired inside `renderRoute` (same rule as `main.ts`), so error-nav behaviours
  are exercised by all specs without extra setup.
- `addError()` suppresses the notification for **401** responses regardless of
  the `navigate` flag — the session-expiry path is intentionally silent.

### Role gating

Pass a `permissions` array to `renderRoute`. The helper calls
`useUser().setPermissions(permissions)` **before** mount, which computes
`bannedRoutes` from `routePermissions`. Navigation to a banned route redirects
away; `getAllowedTabs()` filters nav tabs accordingly.

```ts
import { Permissions } from '@/global';

await renderRoute('/clients', {
  permissions: [Permissions.VIEW_CLIENTS, Permissions.ADD_CLIENT],
  msw: [clientsHandler],
});

// Assert DOM directly — no post-render setPermissions() call needed.
const names = page
  .getByTestId('main-navigation-item-name')
  .elements()
  .map((el) => el.textContent?.trim() ?? '');
expect(names).toContain('Clients');
expect(names).not.toContain('Settings');
```

Do **not** call `useUser().setPermissions()` after `renderRoute` — gating is
already applied before the component mounts. Post-render calls are timing-fragile
and redundant.

When no `permissions` option is passed, `DEFAULT_PERMISSIONS` (defined in
`render-route.ts`) is used — covers the VIEW_CLIENTS / VIEW_CLIENT_DETAILS /
VIEW_CLIENT_SERVICES family needed by most client-flow specs.

### Session state option

`renderRoute` accepts `session?: 'alive' | 'expired'` (default `'alive'`).

```ts
// Boot into a session-expired state:
await renderRoute('/clients', { session: 'expired' });
await expect.element(page.getByTestId('dialog-title')).toBeVisible();
await expect.element(page.getByText('Session expired')).toBeVisible();
```

`session: 'expired'` calls `appState.setSessionAlive(false)` during bootstrap,
causing `XrdApp` to render `XrdLogoutDialog` immediately.

### Triggering fetchSessionStatus

The session-expired dialog also appears when `userStore.fetchSessionStatus()`
returns `{ valid: false }`. Mock the endpoint and call the store action directly:

```ts
await renderRoute('/clients', {
  msw: [
    specHttp.untyped.get('/api/v1/notifications/session-status', () =>
      HttpResponse.json({ valid: false }),
    ),
  ],
});
await useUser().fetchSessionStatus();
await expect.element(page.getByTestId('dialog-title')).toBeVisible();
```

### Error navigation (404 → NotFound)

A view that calls `addError(error, { navigate: true })` on a 404 will trigger
`router.replace({ name: RouteName.NotFound })`:

```ts
const { router } = await renderRoute(`/clients/subsystem/${encodedId}/details`, {
  msw: [
    specHttp.get('/clients/{id}', ({ response }) => response(404).empty()),
  ],
});
await expect.element(page.getByTestId('404-view')).toBeVisible();
expect(router.currentRoute.value.name).toBe('not-found');
```

## Browser-mode limitations — what does NOT fail a spec

**Browser-mode specs do NOT fail on thrown errors or unhandled promise rejections.**
Only a failed `expect()` assertion turns a spec red.

This means:
- A component silently swallowing an error and rendering nothing will pass unless
  you assert that the expected content is visible.
- `addError()` returning a rejected promise will not fail the spec unless you
  assert that no error notification appeared (or that one did appear).
- "No error was thrown" is never a safety net here — it is always true from
  Vitest's perspective in browser mode.

**Rule for authors: assert observable behaviour explicitly.**
After any action that could fail, assert the DOM state you expect to see (or
not see). Do not rely on the absence of an error to confirm success.

```ts
// Wrong — this passes even if fetchData() throws silently:
await renderRoute('/clients');
// (no assertion → spec is green regardless of what the component did)

// Right — assert what the user would actually see:
await renderRoute('/clients');
await expect.element(page.getByTestId('client-name').first()).toBeVisible();
```

This limitation is specific to browser mode (Playwright-driven iframe). Unit
tests running under happy-dom do report unhandled rejections as failures.

## Overlay patterns (v-menu, v-select, dialog, snackbar)

Vuetify overlays teleport their content to `document.body` inside the test
iframe. `page.getByRole()` and `page.getByTestId()` reach teleported content
without special scoping.

### v-select

Click the select control to open the listbox, then pick an option by its
accessible role:

```ts
await page.getByTestId('my-select').click();
await expect.element(page.getByRole('listbox')).toBeVisible();
await page.getByRole('option', { name: 'Beta' }).click();
```

### v-menu

Click the activator. Menu items are teleported to body; use `data-test`
attributes or role selectors on the teleported list items:

```ts
await page.getByTestId('menu-trigger').click();
await expect.element(page.getByTestId('menu-item-option a')).toBeVisible();
await page.getByTestId('menu-item-option a').click();
```

### v-dialog

Dialog content is teleported to body. Focus management and close behaviour work
the same as in a real browser — assert heading visibility and use button clicks
to close:

```ts
await page.getByTestId('open-dialog-btn').click();
await expect.element(page.getByTestId('dialog-heading')).toBeVisible();
await page.getByTestId('dialog-confirm-btn').click();
await expect.element(page.getByTestId('dialog-heading')).not.toBeVisible();
```

### v-snackbar

Before the snackbar is triggered its content is not in the DOM (not just hidden).
Use `query()` to check absence synchronously, then assert visibility after
the trigger:

```ts
// Before trigger: content absent from DOM
expect(page.getByText('Action completed').query()).toBeNull();

await page.getByTestId('show-snackbar-btn').click();

// After trigger: content visible in overlay container
await expect.element(page.getByText('Action completed')).toBeVisible();
```

Do **not** use `not.toBeVisible()` to assert snackbar absence — Vuetify keeps
the outer overlay container in the DOM during the close transition, which causes
`not.toBeVisible()` to time out.

### Viewport

Tests run in Chromium at 1920×1080 (set in `vite.config.ts`). Overlay
positioning is viewport-dependent — Vuetify opens dropdowns downward when there
is space below the anchor. At 1920×1080 there is always enough room below, so
option assertions are stable without any scroll handling.
